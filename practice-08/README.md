## Полученный результат

В результате работы React-приложение было связано с учебным HTTP API.

Реализованы:

- загрузка задач и категорий с сервера;
- передача фильтров серверу через query-параметры;
- создание задач через POST;
- редактирование задач через PATCH;
- переключение статуса через PATCH;
- удаление через DELETE;
- повторная загрузка списка после успешного изменения;
- обработка состояний `loading`, `ready` и `error`;
- сохранение последнего успешного снимка при ошибке обновления;
- отмена устаревших GET-запросов;
- защита от запоздавших ответов;

- отдельная обработка ошибки изменения и ошибки загрузки;

В ПР8 задачи больше не хранятся только в состоянии React. Источником данных является учебный сервер.

Данные сохраняются в памяти процесса API. Поэтому обычная перезагрузка страницы не удаляет созданные или изменённые задачи, пока работает тот же процесс сервера.

После перезапуска API или восстановления демо-набора возвращаются исходные данные.

## Архитектура

Приложение разделено на несколько уровней.

### Компоненты React

Компоненты отвечают за отображение интерфейса:

- `App.jsx` — связывает интерфейс с данными и действиями;
- `TaskFilters.jsx` — серверные фильтры;
- `TaskForm.jsx` — создание и редактирование задачи;
- `TaskList.jsx` — отображение полученной выборки задач.

### `useTaskData`

Основная асинхронная логика находится в:

```text
src/hooks/useTaskData.js
```

Хук отвечает за:

- первоначальную загрузку;
- повторную загрузку;
- состояние загрузки;
- ошибки GET;
- ошибки мутаций;
- создание;
- редактирование;
- переключение статуса;
- удаление;
- восстановление демо-набора;
- отмену запросов;
- защиту от повторных операций.

Хук возвращает:

- `snapshot`;
- `status`;
- `error`;
- `mutationError`;
- `pending`;
- `refresh`;
- `saveTask`;
- `toggleTask`;
- `deleteTask`;
- `resetData`.

### `task-api.js`

`task-api.js` содержит предметные методы работы с задачами и категориями.

Он формирует нужные запросы к API, например:

- получение задач;
- получение категорий;
- создание задачи;
- изменение задачи;
- смену статуса;
- удаление;
- восстановление исходного набора.

### `api-client.js`

`api-client.js` является более низкоуровневым HTTP-клиентом.

Он отвечает за:

- выполнение `fetch`;
- HTTP-методы;
- обработку статусов ответа;
- преобразование серверных ошибок в `ApiError`;
- работу с `AbortSignal`;
- обработку ответа `204 No Content`.

### Зависимости эффекта

Эффект загрузки зависит от:

```text
api
q
completed
priority
categoryId
revision
```

При изменении фильтра или `revision` выполняется новый GET.

`snapshot` и `tasks` в зависимости не входят, потому что они являются результатом загрузки. Если добавить их в зависимости, обновление результата могло бы само запускать новый запрос.

### Cleanup

Для каждого запуска эффекта создаётся собственный `AbortController`.

При cleanup:

1. запрос помечается как неактуальный;
2. вызывается `abort()`.

Это позволяет отменять старые GET-запросы при смене фильтров или размонтировании компонента.

### `useRef`

В работе используются служебные ссылки через `useRef`.

`mountedRef` показывает, смонтирован ли компонент.

`mutationControllerRef` хранит контроллер текущей операции изменения и одновременно используется как немедленная блокировка повторного вызова.

### Отличие от ПР7

В ПР7:

- задачи хранились локально;
- фильтрация выполнялась по массиву в React;
- id назначался клиентом;
- операции были синхронными;
- после перезагрузки возвращался исходный набор.

В ПР8:

- задачи находятся на сервере;
- фильтры передаются API;
- id назначается сервером;
- операции выполняются асинхронно;
- после POST/PATCH/DELETE выполняется новый GET;
- данные сохраняются после перезагрузки страницы, пока сервер не перезапущен.

## Загрузка и изменения

### Подавление старых ответов

Каждая загрузка имеет:

- собственный `AbortController`;
- локальный признак `active`.

Перед записью результата проверяется, является ли запрос ещё актуальным.

Если пользователь быстро изменил фильтр, старый запрос отменяется и его поздний результат не заменяет новую выборку.

Проверка выполняется как для успешного ответа, так и для ошибки.

### Блокировка повторной мутации

Для текущей операции изменения используется:

```text
mutationControllerRef
```

Контроллер записывается в `ref` до первого `await`.

Если во время выполнения операции происходит ещё один вызов, функция сразу возвращает `false`.

Это защищает от создания двух одинаковых задач при двойном нажатии на кнопку сохранения.

После завершения операции блокировка снимается в `finally`.

### Ошибка изменения и ошибка GET

Ошибки разделены на два состояния:

```text
error
```

— ошибка загрузки GET.

```text
mutationError
```

— ошибка POST, PATCH или DELETE.

Успешная мутация и последующая загрузка рассматриваются отдельно.

Например:

1. POST успешно создал задачу;
2. после него запускается новый GET;
3. GET завершился ошибкой.

В такой ситуации создание всё равно считается успешным. Ошибка повторной загрузки не превращает успешный POST в ошибку мутации.

Последний успешный снимок при этом сохраняется.

### Черновик формы при ошибке

Форма вызывает асинхронный `onSave`.

Если операция возвращает:

```text
false
```

введённые значения не очищаются.

Пользователь видит ошибку и может повторить сохранение после устранения проблемы.

Только при:

```text
true
```

форма очищается или выходит из режима редактирования.

## Контрольные вопросы

### 1. Зачем для загрузки данных нужен эффект, а не запрос в теле компонента?

Тело компонента должно описывать отображение интерфейса. Сетевой запрос является побочным эффектом, поэтому выполняется через `useEffect`.

Иначе запрос мог бы выполняться при каждом рендере.

### 2. Когда React вызывает cleanup?

Cleanup вызывается перед повторным выполнением эффекта при изменении его зависимостей и при размонтировании компонента.

### 3. Почему callback эффекта не объявляется `async`?

`useEffect` ожидает, что функция эффекта вернёт либо ничего, либо функцию cleanup.

`async`-функция всегда возвращает Promise, поэтому асинхронную функцию создают внутри эффекта и вызывают отдельно.

### 4. Какие зависимости нужны загрузке и почему в них нет `snapshot`?

Загрузка зависит от:

- `api`;
- `q`;
- `completed`;
- `priority`;
- `categoryId`;
- `revision`.

`snapshot` является результатом загрузки. Если добавить его в зависимости, обновление результата могло бы запускать новый запрос.

### 5. Почему стабильная ссылка на api важна?

Если объект `api` создаётся заново при каждом рендере, React будет считать зависимость изменившейся и повторно запускать эффект.

Это может привести к постоянным запросам.

### 6. Зачем кроме AbortController проверять актуальность ответа?

Не любая реализация API обязана корректно остановиться после `abort()`.

Поэтому дополнительно проверяется локальный признак актуальности, чтобы старый ответ не мог изменить состояние.

### 7. Почему защита от устаревшего результата нужна и в catch?

Старый запрос может завершиться поздней ошибкой.

Без проверки актуальности эта ошибка могла бы заменить успешное состояние, полученное более новым запросом.

### 8. Что проверяет дополнительный цикл StrictMode?

В режиме разработки React дополнительно выполняет последовательность:

```text
setup → cleanup → setup
```

Это помогает обнаруживать эффекты, которые неправильно очищают ресурсы или имеют нежелательные побочные действия.

### 9. Почему одного `pending` в state недостаточно для двух синхронных вызовов?

Обновление state происходит не мгновенно.

Два почти одновременных вызова могут оба увидеть старое значение `pending=false`.

Поэтому для немедленной блокировки используется `useRef`, который изменяется синхронно до первого `await`.

### 10. Что означает `true`, возвращённое `saveTask`, если повторный GET завершился ошибкой?

Это означает, что сама операция сохранения была подтверждена сервером и выполнена успешно.

Ошибка последующего GET является отдельной ошибкой обновления данных.

### 11. Почему нельзя автоматически повторять POST после тайм-аута?

Клиент может не знать, успел сервер создать запись или нет.

Если автоматически повторить POST, возможно создание дубликата.

Сначала безопаснее обновить список и проверить результат.

### 12. Почему смена фильтров не должна отменять мутацию?

Фильтр относится к операции чтения.

POST, PATCH или DELETE является отдельной пользовательской операцией и не должен отменяться только из-за изменения отображаемой выборки.

### 13. Что происходит с серверной операцией после отмены клиентского ожидания?

Отмена клиентского запроса не гарантирует отмену операции на сервере.

Сервер мог уже начать или завершить изменение данных.

### 14. Чем `meta.total` отличается от общего числа записей на сервере?

`meta.total` показывает количество записей в последней серверной выборке после применения фильтров.

Это не обязательно общее количество всех задач на сервере.

### 15. Какие сценарии не проверяются jsdom и требуют браузера?

В браузере дополнительно проверяются:

- настоящий CORS;
- вкладка Network;
- визуальное отображение;
- работа реальной формы;
- действия пользователя;
- production preview.
