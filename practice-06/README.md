## 3. Реализация

### 3.1. HTTP-клиент

В файле `src/api-client.js` был реализован общий HTTP-клиент.

Поддерживаются методы:

```text
GET
POST
PATCH
DELETE
```

Метод запроса приводится к верхнему регистру. Для всех запросов добавляется заголовок:

```text
Accept: application/json
```

Если запрос содержит тело, объект преобразуется в JSON с помощью `JSON.stringify`, после чего добавляется:

```text
Content-Type: application/json
```

Для `GET` передача тела запрещена.

Клиент различает следующие виды ошибок:

```text
http
network
invalid-response
timeout
aborted
```

При ответе `204 No Content` клиент возвращает `null` и не пытается выполнять `response.json()`. Также сохранена поддержка тайм-аута и внешней отмены запроса через `AbortSignal`.

### 3.2. Доменный API

В файле `src/task-api.js` были реализованы операции:

```text
getTasks
getTaskById
getCategories
loadInitialData
createTask
updateTask
setTaskCompleted
deleteTask
resetDemoData
```

`getTasks` получает список задач с фильтрами.

`getTaskById` получает одну задачу по идентификатору.

`createTask` создаёт новую задачу через `POST`.

`updateTask` изменяет данные задачи через `PATCH`.

`setTaskCompleted` изменяет состояние `completed`.

`deleteTask` удаляет задачу через `DELETE`.

`resetDemoData` восстанавливает исходный набор учебных данных.

После получения ответа данные проверяются функциями проверки схемы. Проверяются поля задач и категорий, идентификаторы, типы данных и количество элементов.

Начальная загрузка задач и категорий выполняется параллельно через `Promise.all`.

### 3.3. Состояния интерфейса

В приложении используются четыре основных состояния списка:

```text
loading
ready
empty
error
```

`loading` устанавливается во время выполнения запроса.

`ready` используется после успешной загрузки непустого списка задач.

`empty` устанавливается, если запрос выполнен успешно, но подходящих задач нет.

`error` используется при ошибке загрузки.

При повторной загрузке состояние снова переключается в `loading`, после чего устанавливается новое состояние в зависимости от результата запроса.

### 3.4. Изменение данных

Приложение поддерживает основные операции с задачами.

При создании задачи данные формы сначала проходят клиентскую проверку. После этого выполняется `POST` на сервер. Идентификатор новой задачи назначается сервером.

При редактировании выполняется `PATCH` с изменёнными полями.

Для изменения статуса задачи выполняется `PATCH` с новым значением `completed`.

При удалении выполняется `DELETE`.

После успешной изменяющей операции приложение повторно загружает список задач с текущими фильтрами. Таким образом интерфейс отображает состояние, подтверждённое сервером.

На время изменяющей операции соответствующие действия блокируются, чтобы предотвратить повторную отправку одинаковых запросов.

### 3.5. Защита от устаревшего ответа

Для защиты от нескольких одновременно выполняющихся загрузок используются два механизма.

Первый механизм — `AbortController`. Перед началом нового запроса предыдущая загрузка отменяется.

Второй механизм — номер последовательности загрузки. Каждому новому запросу присваивается новый номер. Полученный результат применяется к интерфейсу только в том случае, если номер запроса соответствует последнему запущенному запросу.

Благодаря этому более старый запрос не может перезаписать результат более нового запроса.

Отмена запроса с типом `aborted` не отображается пользователю как ошибка.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**

`fetch` считает ответ `404` успешно полученным HTTP-ответом. Promise отклоняется в основном при сетевой ошибке или отмене запроса. Поэтому HTTP-статус необходимо отдельно проверять через `response.ok`.

2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**

Статус `204 No Content` означает, что тело ответа отсутствует. Если вызвать `response.json()`, будет выполнена попытка разобрать пустое тело как JSON, что приведёт к ошибке. Поэтому при `204` клиент сразу возвращает `null`.

3. **Чем состояние `empty` отличается от `error`?**

`empty` означает, что запрос выполнен успешно, но сервер не вернул ни одной подходящей задачи.

`error` означает, что запрос не удалось успешно выполнить, например из-за сетевой ошибки или ошибки сервера.

Таким образом `empty` является нормальным состоянием данных, а `error` — ошибкой выполнения операции.

4. **Зачем отменять предыдущий запрос при смене фильтров?**

Если пользователь быстро изменит фильтры несколько раз, более старый запрос может завершиться позже нового и показать устаревшие данные.

Отмена предыдущего запроса уменьшает вероятность такой ситуации. Дополнительно используется номер запроса, поэтому старый ответ не может изменить интерфейс.

5. **Почему после мутации список повторно запрашивается у API?**

Сервер является основным источником данных. После создания, редактирования, смены статуса или удаления приложение повторно запрашивает список с текущими фильтрами.

Это позволяет отображать именно то состояние, которое было подтверждено сервером, и не хранить отдельную несогласованную копию данных в браузере.
