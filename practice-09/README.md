## Цель и результат

Цель практической работы — изучить создание собственного HTTP API на Node.js и Express, обработку HTTP-запросов, маршрутизацию, проверку входных параметров, фильтрацию данных и единый формат ошибок.

В ходе работы был реализован Express-сервер, который:

- возвращает состояние сервиса;
- возвращает список категорий;
- возвращает список задач;
- возвращает отдельную задачу по id;
- фильтрует задачи по статусу;
- фильтрует задачи по приоритету;
- фильтрует задачи по категории;
- выполняет поиск по названию;
- объединяет фильтры через условие И;
- проверяет query-параметры;
- отклоняет неизвестные и повторяющиеся параметры;
- проверяет корректность id;
- различает ошибки 400, 404 и 405;
- поддерживает HEAD;
- поддерживает OPTIONS;
- возвращает CORS-заголовки;
- не изменяет исходные данные при операциях чтения.

Данные хранятся в памяти процесса. PostgreSQL, авторизация, создание, редактирование и удаление задач в ПР9 не реализуются. Эти операции относятся к следующей практической работе.

## Реализация

### `validation.js`

Модуль отвечает за проверку и преобразование входных параметров.

Реализованы функции:

```js
parsePositiveId(raw)
parseFilters(searchParams)
```

`parsePositiveId` проверяет всю строку идентификатора.

Допускаются только положительные целые значения без:

- ведущих нулей;
- пробелов;
- дробной части;
- экспоненциальной записи;
- дополнительных символов.

Также проверяется:

```js
Number.isSafeInteger(value)
```

Например:

```text
4     → допустимо
01    → недопустимо
4abc  → недопустимо
1.5   → недопустимо
0     → недопустимо
```

Использовать только `parseInt` нельзя, потому что:

```js
parseInt('4abc')
```

вернул бы число `4`.

### Проверка фильтров

Разрешены только четыре query-параметра:

```text
completed
priority
categoryId
q
```

Неизвестные параметры отклоняются с:

```text
400 INVALID_QUERY
```

Повторение любого параметра также запрещено.

Например:

```text
?q=a&q=b
```

возвращает ошибку.

### Нормализация `false`

Значение:

```text
completed=false
```

нельзя преобразовывать через:

```js
Boolean('false')
```

потому что результатом будет `true`.

Поэтому сначала проверяется строка:

```js
raw === 'true'
```

После проверки допустимых значений строка преобразуется в boolean.

### `task-service.js`

Модуль содержит предметную логику работы с массивом задач.

Реализованы:

```js
selectTasks(tasks, filters)
findTask(tasks, id)
```

`selectTasks` применяет все фильтры одновременно через условие И.

Исходный массив не изменяется.

Поиск выполняется по названию без учёта регистра через:

```js
toLocaleLowerCase('ru-RU')
```

`findTask` ищет запись именно по полю:

```js
task.id
```

а не по индексу массива.

Это важно, потому что идентификаторы задач имеют пропуски.

### `store.js`

`store.js` отвечает за данные конкретного экземпляра приложения.

Маршруты не обращаются напрямую к `data.js`, а используют методы хранилища:

```js
store.listCategories()
store.listTasks(filters)
store.getTask(id)
```

Это отделяет хранение данных от HTTP-слоя.

### `routes.js`

`routes.js` связывает HTTP-запросы с логикой приложения.

Реализованы маршруты:

```text
GET /api/health
GET /api/categories
GET /api/tasks
GET /api/tasks/:id
```

Для списка задач `req.originalUrl` разбирается через:

```js
new URL(req.originalUrl, 'http://localhost')
```

После этого `URLSearchParams` передаются в `parseFilters`.

### `app.js`

`app.js` собирает Express-приложение:

- подключает общие middleware;
- устанавливает CORS-заголовки;
- обрабатывает OPTIONS;
- подключает Router;
- подключает обработчик неизвестных маршрутов;
- подключает обработчик ошибок.

`app.js` не открывает сетевой порт.

### `server.js`

`server.js` отвечает за запуск приложения и выбор порта.

Такое разделение позволяет тестам создавать приложение отдельно и запускать его на свободном тестовом порту.

### Порядок middleware

Порядок обработчиков имеет значение.

Используется следующая последовательность:

1. общие заголовки и OPTIONS;
2. GET-маршруты;
3. обработчики 405 для известных маршрутов;
4. обработчик 404 неизвестного маршрута;
5. обработчик ошибок.

Обработчики `405` расположены после GET-маршрутов, чтобы они не перехватывали допустимые запросы чтения.

Например:

```text
GET /api/tasks/4abc
```

возвращает:

```text
400 INVALID_ID
```

Параметр:

```text
?completed=0
```

возвращает:

```text
400 INVALID_QUERY
```

### Ошибка 404

Если идентификатор синтаксически правильный, но задачи нет:

```text
GET /api/tasks/2
```

возвращается:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача не найдена.",
    "details": {
      "id": 2
    }
  }
}
```

Статус:

```text
404 Not Found
```

Неизвестный маршрут также возвращает 404, но с другим кодом:

```text
ROUTE_NOT_FOUND
```

### Ошибка 405

Изменяющие методы в ПР9 ещё не реализованы.

Например:

```text
POST /api/tasks
```

возвращает:

```text
405 METHOD_NOT_ALLOWED
```

и заголовок:

```text
Allow: GET, HEAD, OPTIONS
```

### `meta.total`

`meta.total` содержит количество задач именно в полученной выборке.

Например, если фильтр вернул 7 задач:

```json
{
  "meta": {
    "total": 7
  }
}
```

Это не обязательно общее количество задач в хранилище.

Без фильтров исходный набор содержит 12 задач.

### Граница ПР9 и ПР10

В ПР9 реализуются только операции чтения.

Доступны:

```text
GET
HEAD
OPTIONS
```

Операции:

```text
POST
PATCH
DELETE
```

для задач пока возвращают `405`.

Создание, редактирование, удаление и полное подключение клиента ПР8 относятся к ПР10.

## Контрольные вопросы

### 1. Чем JavaScript в Node.js отличается от JavaScript в браузере?

Node.js выполняет JavaScript вне браузера.

В Node.js нет браузерных объектов вроде:

```text
window
document
DOM
```

Зато доступны серверные возможности, например работа с сетью, файлами и запуск HTTP-сервера.

### 2. Что определяет выбор маршрута: путь, query или HTTP-метод?

Маршрут определяется HTTP-методом и путём.

Например:

```text
GET /api/tasks
```

Query-параметры:

```text
?completed=false
```

не являются частью пути маршрута.

### 3. Чем `req.params` отличается от query-параметров?

`req.params` содержит параметры, являющиеся частью пути.

Например для:

```text
/tasks/:id
```

при запросе:

```text
/tasks/4
```

значение:

```js
req.params.id
```

будет равно `"4"`.

Query-параметры находятся после `?`:

```text
/tasks?priority=high
```

### 4. Почему строка `'false'` требует явного преобразования?

Потому что:

```js
Boolean('false')
```

возвращает `true`.

Любая непустая строка является truthy.

Поэтому строка сначала проверяется и затем преобразуется явным сравнением.

### 5. Зачем проверять весь id и `Number.isSafeInteger`?

Проверка всей строки не позволяет принять значения вроде:

```text
4abc
1.5
01
```

`Number.isSafeInteger` дополнительно гарантирует, что число находится в безопасном диапазоне JavaScript.

### 6. Почему пустая выборка имеет статус 200, а отсутствующая задача — 404?

Пустая выборка означает, что запрос списка выполнен успешно, но подходящих записей нет.

Поэтому возвращается:

```text
200
data: []
```

При запросе конкретной задачи клиент обращается к определённому ресурсу. Если такого ресурса нет, возвращается 404.

### 7. В чём различие `TASK_NOT_FOUND` и `ROUTE_NOT_FOUND`?

`TASK_NOT_FOUND` означает, что маршрут существует, но задачи с указанным id нет.

`ROUTE_NOT_FOUND` означает, что самого запрошенного маршрута в API не существует.

### 8. Чем 405 отличается от 404 и зачем нужен Allow?

404 означает, что путь не существует.

405 означает, что путь существует, но HTTP-метод для него не поддерживается.

Заголовок `Allow` показывает допустимые методы:

```text
GET, HEAD, OPTIONS
```

### 9. Что означает `meta.total` при активных фильтрах?

`meta.total` содержит количество задач в текущей отфильтрованной выборке.

Это не обязательно общее количество задач в хранилище.

### 10. Как порядок middleware влияет на результат?

Express выполняет middleware в порядке их регистрации.

Если 404 поставить до маршрутов, запрос не дойдёт до нужного обработчика.

Если обработчик 405 поставить перед GET, он может перехватить корректный GET.

### 11. Почему обработчик ошибок имеет четыре параметра?

Express распознаёт error middleware по сигнатуре:

```js
(error, req, res, next)
```

Даже если `next` внутри функции не используется, четвёртый параметр нужен для правильного определения обработчика ошибок.

### 12. Зачем фабрика приложения отделена от открытия порта?

`createApp()` создаёт приложение, но не запускает сервер.

Это позволяет тестам создавать отдельные экземпляры приложения и запускать их на свободных портах.

`server.js` уже отвечает непосредственно за открытие порта.

### 13. Какие данные допустимо отправлять клиенту при внутренней ошибке?

Клиенту можно отправить:

- HTTP-статус;
- безопасный код ошибки;
- понятное сообщение.

Не следует отправлять:

- stack trace;
- внутренние пути файлов;
- технические данные сервера;
- секреты.

### 14. Почему CORS не является авторизацией?

CORS управляет тем, может ли JavaScript одного origin читать ответ другого origin в браузере.

Он не проверяет личность пользователя и не запрещает прямые запросы к серверу.

Поэтому CORS не заменяет авторизацию.

### 15. Какие изменения потребуются в ПР10 для подключения всех действий клиента ПР8?

Потребуется реализовать изменяющие HTTP-операции:

```text
POST
PATCH
DELETE
```

Также потребуется:

- серверная валидация тела запросов;
- создание задач;
- редактирование задач;
- переключение `completed`;
- удаление задач;
- назначение новых id;
- соответствующие HTTP-статусы и ошибки.

После этого собственный сервер сможет полностью заменить учебный API для клиента ПР8.
