## Эксперимент с очередями выполнения

До запуска `npm run example:order` был записан прогноз порядка меток.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A B C D E F` | Сначала выполняется синхронный код, затем микрозадачи Promise и продолжение после `await`, после них — таймер |
| Фактический результат | `A B C D E F` | Фактический порядок совпал с прогнозом |

К синхронному коду относятся сообщения `A`, `B` и `C`. Они выполняются сразу в текущем стеке вызовов.

Сообщения `D` и `E` относятся к микрозадачам. `D` добавляется через `Promise.resolve().then(...)`, а `E` является продолжением `async`-функции после `await`.

Таймер `F` с задержкой `0` не выполняется немедленно. Его обработчик попадает в очередь задач и выполняется только после завершения синхронного кода и очереди микрозадач.

Дополнительно был добавлен собственный обработчик:

```js
Promise.resolve().then(() => {
  log("G: собственная микрозадача");
});
```

Прогноз и фактический результат:

```text
A B C D G E F
```

Если удалить один из обработчиков Promise, соответствующая ему микрозадача исчезнет, а остальные сообщения сохранят свой относительный порядок.

### `/health`

Сервер отвечает статусом `200` и JSON со статусом `ok`.

### `/tasks/25`

Получен статус `200`.

Ответ:

```json
{
  "data": {
    "id": 25,
    "title": "Исправить обработку ошибок",
    "completed": true,
    "priority": "high",
    "categoryId": 2
  }
}
```

### `/tasks/999`

Получен статус `404`.

Ответ:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача с id 999 не найдена.",
    "details": {
      "id": 999
    }
  }
}
```

Таким образом, ответ `404` является HTTP-ответом сервера, а не сетевой ошибкой.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API, маршруты задач, категорий и отладочных запросов |
| `src/api-client.js` | Формирование URL, выполнение `fetch`, JSON, тайм-аут, отмена и единый тип `ApiError` |
| `src/task-api.js` | Предметные методы задач и категорий, фильтры и проверка схемы полученных данных |
| `src/variant.js` | Номер индивидуального варианта и его фильтры |
| `src/main.js` | Контрольный сценарий работы клиента в терминале |

`fetchFn` передаётся аргументом в `createApiClient`, чтобы при модульных проверках можно было заменить настоящий `fetch` тестовой функцией и проверять клиент без реальной сети.

HTTP-ошибки обрабатываются отдельно от сетевых, потому что при статусах `404`, `400` или `503` сервер всё равно вернул объект `Response`. Сетевая ошибка означает, что нормальный HTTP-ответ вообще не был получен.

Даже после успешного разбора JSON данные проверяются по контракту. Синтаксически корректный JSON может содержать неверные типы, отсутствующие поля, повторяющиеся `id` или неправильный `meta.total`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | Проверяется абсолютный `http/https` URL, отсутствие query/hash, удаляется завершающий `/` | `OK 01`, `OK 04` |
| Кодирование query-параметров | Используется `URL` и `URLSearchParams`; `undefined`, `null`, `""` пропускаются, `false` и `0` сохраняются | `OK 02`, `OK 03` |
| Заголовок `Accept` | Для GET передаётся `Accept: application/json` | `OK 05` |
| Проверка `response.ok` | Неуспешный статус преобразуется в `ApiError(kind: "http")` | `OK 08`, `OK 09`, `OK 16` |
| Проверка `Content-Type` | Успешный ответ должен содержать `application/json` | `OK 10` |
| Разбор JSON | Используется `await response.json()`, ошибка разбора становится `invalid-response` | `OK 06`, `OK 11` |
| Ограничение времени | Используется `AbortSignal.timeout(timeoutMs)` | `OK 14` |
| Внешняя отмена | Внешний `AbortSignal` объединяется с тайм-аутом через `AbortSignal.any()` | `OK 15` |

Успешный ответ со статусом `204` преобразуется в `null`.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]` |

| `getCategories()` | `1 — Учёба`, `2 — Проект`, `3 — Организация` |
| `loadInitialData(...)` | Объект `{ tasks, categories, meta }`, задачи и категории загружаются параллельно |

Для задачи проверяются:

- `id` — положительное безопасное целое число;
- `title` — непустая строка длиной не более 100 символов после `trim`;
- `completed` — boolean;
- `priority` — `low`, `medium` или `high`;
- `categoryId` — положительное безопасное целое число.

Для категории проверяются:

- положительный безопасный целый `id`;
- непустое строковое `name` длиной не более 100 символов.

Для коллекций дополнительно проверяются уникальность `id` и соответствие:

```text
meta.total === data.length
```

При нарушении схемы создаётся:

```text
ApiError
kind: "invalid-response"
```

## Отладка

Основные точки останова:

1. перед вызовом `fetchFn`;
2. сразу после получения `Response`;
3. перед `response.json()`;
4. внутри обработки ошибок.

Для успешного запроса проверялись:

```text
URL:
http://127.0.0.1:5505/api/tasks?completed=false&priority=high

response.status:
200

response.ok:
true

Content-Type:
application/json; charset=utf-8

Полученные id:
[4, 13, 34]
```

Для ошибочного запроса задачи `999`:

```text
URL:
http://127.0.0.1:5505/api/tasks/999

response.status:
404

response.ok:
false

Content-Type:
application/json; charset=utf-8

payload.error.code:
TASK_NOT_FOUND
```

Итоговый объект ошибки содержит:

```text
kind: http
status: 404
code: TASK_NOT_FOUND
details: { id: 999 }
```

В ходе отладки была обнаружена ошибка проверки конфигурации `createApiClient`: для неверной конфигурации первоначально создавался обычный `Error`, тогда как требовался `TypeError`. После отдельной проверки `baseUrl`, `fetchFn` и целочисленного положительного `timeoutMs` все проверки стали успешными.

Также при ручной проверке тайм-аута первоначально возникла ошибка:

```text
ReferenceError: client is not defined
```

Причина заключалась в области видимости: `client` создавался внутри блока `try`. Проверка тайм-аута и отмены была перенесена внутрь той же области видимости.

## Вывод

В практической работе был реализован клиент для получения данных из локального HTTP API.

Функция `buildUrl` формирует адрес запроса и корректно кодирует query-параметры. Общий клиент `createApiClient` выполняет GET-запросы, проверяет HTTP-статус и `Content-Type`, разбирает JSON, поддерживает тайм-аут и внешнюю отмену.

Ошибки разделены на пять типов:

- `http` — сервер доступен, но вернул ошибочный HTTP-статус;
- `network` — ответ от сервера не был получен;
- `invalid-response` — ответ имеет неверный формат, JSON или структуру;
- `timeout` — превышено разрешённое время ожидания;
- `aborted` — запрос отменён вызывающим кодом.

В `task-api.js` реализованы методы получения задач и категорий, нормализация фильтров и проверка структуры данных.

Независимые запросы задач и категорий выполняются параллельно через `Promise.all`. Эксперимент показал, что при двух искусственных задержках по 150 мс последовательное выполнение занимало около 309–325 мс, а параллельное — около 156–173 мс.

Индивидуальный вариант № 1 с фильтром `{ completed: false }` выполнен успешно: получено 7 задач с id `[4, 7, 13, 19, 22, 28, 34]`.

Основные, интеграционные и собственные проверки завершились успешно.
